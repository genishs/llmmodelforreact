# 모델 학습 개념 정리 — React 코드 어시스턴트로 이해하기

> 목적: 우리 프로젝트(로컬 React 코드 어시스턴트)를 예로 들어 **파라미터·정밀도(bf16/4bit/nf4)·LoRA/QLoRA** 개념을 정리한 학습 문서.
> 작성: halo-ubuntu-pm(피 선생), 2026-07. 편하게 읽으시라고 문서화.

---

## Part 1. 지금까지의 학습 써머리

우리가 만드는 것 = **로컬 React 코드 어시스턴트**: JS/JSX → 타입 안전한 TS/TSX 변환, egov·프로젝트 패턴 준수, 로컬 디바이스에서 직접 학습·구동.

| 단계 | 베이스 | 방식 | 결과 |
|---|---|---|---|
| 초기 | Qwen2.5-Coder **1.5B** | CPU LoRA | 데모 수준 (eval_loss ~0.77) |
| 확장 | **7B** | Windows DirectML LoRA | v1~v5, seq384~512에서 품질 벽 |
| 경쟁 | **14B** | DirectML (seq256 강제) | heldout7 **62.9%** |
| **현재** | **7B / 14B** | **Linux ROCm bf16** | 7B val 0.496, **14B val 0.481** (채점 중) |
| 큐 | **32B / 72B(70B)** | ROCm **4bit(QLoRA)** | Windows 불가 → Linux 개방 |

### 핵심 교훈 (양 장비 독립 확증)
무작정 모델을 키운다고 좋아지지 않았다. **데이터 품질 + LoRA가 건드리는 부위(MLP 포함) > 순수 파라미터 크기.**
예: 14B(62.9%)가 7B 챔피언(80%)보다 낮게 나온 적도 있음 — 그 14B는 qkvo만·적은 데이터·seq256이라 "레버"를 안 썼기 때문.
→ 지금 32B/70B는 *"크기를 극한으로 키우면 마침내 그 벽을 넘나?"* 를 검증하는 실험.

### Windows → Linux 전환의 이유 (한 줄)
Windows(DirectML)는 **bf16 불가·4bit 불가·전용 VRAM ~39GB 하드캡·공유메모리 ~8GB 캡**이라 14B 고seq/32B+가 막혔다.
Linux(ROCm)는 **bf16·4bit 지원 + 통합메모리 60GB를 GPU가 동적 사용** → 14B 고seq, 32B/70B QLoRA가 열렸다. (실측: 학습이 실제 54.9GB 할당 성공)

## Part 2. 핵심 용어 강의

### ① 파라미터(Parameter)
모델이 학습으로 얻은 **"조절 손잡이(가중치, weight)"** 하나하나. 7B = **70억 개**의 손잡이.

- **많을수록** = 더 많은 지식·문맥·코드 패턴 수용 (긴 컴포넌트, 복잡한 타입, 미묘한 관용구 이해력↑)
- **하지만** = 메모리↑·속도↓, 그리고 우리 프로젝트가 보여줬듯 **"많다=무조건 좋다"는 아님**
- **React 어시스턴트 관점**: 7~14B면 이미 "JSX→TSX 변환, 타입 추론"은 충분. 32~70B는 *더 길고 어려운 파일, 더 정확한 타입*에서 차이가 나는지 보는 것.

### ② 정밀도 = 손잡이 하나를 "몇 비트로" 저장하나 (fp16 / bf16 / 4bit)
각 파라미터는 **숫자**다. 그 숫자를 **몇 비트로 표현하느냐**가 정밀도.

| 표현 | 비트/파라미터 | 비유 | 메모리 (14B 기준) |
|---|---|---|---|
| **fp16 / bf16** | 16비트 (2바이트) | 정밀한 다이얼 | 14B × 2 = **28GB** |
| **8bit** | 8비트 (1바이트) | 256단계 | 14GB |
| **4bit** | 4비트 (0.5바이트) | 16단계 거친 다이얼 | 14B × 0.5 = **7GB** |

- **fp16** = 표준 16비트 부동소수점.
- **bf16** ("brain float 16") = 딥러닝용 16비트. fp16과 같은 2바이트지만 **지수부를 넓게** 잡아 학습이 더 안정적(값 범위가 넓어 발산·언더플로 적음). **DirectML은 bf16을 못 해서** Linux로 온 이유 중 하나.
- **4bit** = 손잡이를 4비트(16단계)로 압축 → **메모리 1/4**. 미세 정밀도는 손실. **70B 같은 거인을 작은 기계에 올리는 유일한 방법.**

**메모리 빠른 표 (우리 모델들):**

| 모델 | 파라미터 | bf16 (2B/param) | 4bit/nf4 (~0.5B/param) |
|---|---|---|---|
| 1.5B | 15억 | 3GB | ~1GB |
| 7B | 76억 | 15GB | 4.5GB |
| 14B | 147억 | 29GB | 8.5GB |
| 32B | 325억 | 65GB (불가, 60GB 초과) | 19GB |
| 72B | 720억 | 144GB (불가) | 39GB |

→ **32B·70B는 bf16이면 우리 기계(60GB)에 안 들어감. 4bit라야 들어간다.** 이게 4bit가 필수인 이유.

### ③ nf4 = "똑똑한 4bit" (NormalFloat 4-bit)
그냥 4bit(정수 16단계 균등분할)는 낭비가 크다. 신경망 가중치는 **대부분 0 근처에 몰린 정규분포(normal distribution)** 를 따르기 때문.

- **nf4** = 16단계 눈금을 **균등이 아니라 정규분포 모양에 맞춰** 배치 → 값이 실제로 몰려있는 **0 근처에 눈금을 촘촘히**, 바깥쪽은 성기게.
- 효과: **같은 4비트인데 정보 손실 최소화.** QLoRA 논문(Dettmers et al.)의 핵심 아이디어.
- 우리가 Windows에서 받은 **Qwen2.5-72B / Llama-3.3-70B가 바로 이 nf4 사전양자화판**(각 37~39GB). 그래서 fp16 140GB를 안 받아도 됐다.
- **double-quantization(이중 양자화)**: 양자화에 쓰는 상수(absmax 등)까지 한 번 더 압축 → 메모리 추가 절약.

### ④ LoRA / QLoRA = 어떻게 "효율적으로" 학습하나
70억 손잡이를 **전부** 다시 돌리면(full fine-tuning) 메모리·시간이 폭발한다. 그래서:

**LoRA (Low-Rank Adaptation):**
- 거대한 **베이스는 얼려두고(frozen)**, 옆에 작은 **"보정 손잡이(어댑터)"** 만 붙여 그것만 학습.
- 전체의 **0.1~0.5%**만 훈련. 우리 14B는 68.8M개만 학습(0.46%) → 어댑터 파일 **263MB**뿐.
- 베이스를 안 건드리니 **여러 특화본을 갈아끼울 수 있음**(React용, 다른 도메인용…).
- **rank(r)** = 보정 손잡이의 "폭". 우리는 r16 사용. 클수록 표현력↑·용량↑·크기↑ (너무 크면 과적합).
- **qkvo / MLP** = 어댑터를 **어느 부위에** 붙이나:
  - `q_proj, k_proj, v_proj, o_proj` = 어텐션(문맥을 어디에 주목할지)
  - `gate_proj, up_proj, down_proj` = MLP(각 토큰을 어떻게 변환할지)
  - **MLP까지 붙이면 학습 용량↑** = 4060이 증명하고 우리도 채택한 "레버". (우리 7B/14B는 qkvo+MLP)

**QLoRA = Quantized + LoRA:**
- **베이스를 4bit(nf4)로 압축**해 메모리에 올리고, 그 위에 **LoRA 어댑터는 높은 정밀도로** 학습.
- 이것이 **70B를 60GB 기계에 올리는 마법**: 70B × 0.5B = 40GB(4bit 베이스) + 작은 어댑터. bf16이면 140GB라 절대 불가.
- 트레이드오프: 베이스가 4bit라 미세 정밀도 손실이 있으나, nf4 + 학습 어댑터가 대부분 보완.

## Part 3. 종합 — 우리 어시스턴트 구조

```
[베이스 모델]  Qwen2.5-Coder = 이미 코드를 아는 "뇌"
       │  (7B/14B는 bf16 통째로, 32B/70B는 nf4 4bit로 압축해 메모리에 올림)
       ▼
[LoRA 어댑터]  우리 데이터로 학습한 "React/TS 특화 보정" (수백 MB)
       │  = JSX→TSX 변환, 타입 추론, egov 패턴, im_start 토큰누수 억제 …
       ▼
[React 코드 어시스턴트]  = 베이스 + 어댑터
```

| 체급 | 정밀도 | 왜 |
|---|---|---|
| 7B | bf16 통째 | 빠름, 이미 꽤 잘함 |
| 14B | bf16, 고seq | 문맥·정확도↑, 지금 62.9% 넘나 채점 중 |
| 32B / 70B | **nf4 QLoRA** | bf16 불가(메모리 초과) → 4bit만이 유일한 길, "크기가 벽을 넘나" 실험 |

**한 줄 요약**
> **파라미터**(손잡이 수) = "뇌 크기" · **정밀도**(bf16/4bit/nf4) = "손잡이를 몇 비트로 저장하나" · **LoRA/QLoRA** = "큰 뇌를 안 건드리고 작은 보정만 얹어 싸게 특화하는 법."
> 이 셋의 조합으로 작은 기계에서 70B까지 React 특화를 시도한다.

## 부록. 더 깊이 (자주 나오는 후속 질문)

- **왜 7B가 14B를 이기기도 했나?** 그 14B는 qkvo만·적은 데이터·seq256(문맥 짧음)이라 "레버"를 안 썼다. 반면 7B 챔피언은 qkvo+MLP·좋은 데이터·seq512. → **크기보다 구성**. 지금 14B는 bf16+MLP+seq1024로 3레버를 다 켰으니 결과가 다를 것.
- **val_loss vs 실제 채점 점수?** val_loss는 "다음 토큰을 얼마나 잘 맞추나"의 대리지표(낮을수록 좋음). 하지만 **실제 tsc 컴파일 통과율(%)** 이 진짜 목표. 둘은 대체로 같은 방향이나 항상 일치하진 않음 → 그래서 heldout 캐논으로 **직접 채점**한다.
- **seq(시퀀스 길이)?** 한 번에 보는 토큰 수. 짧으면(seq256) 긴 컴포넌트가 잘려서 학습·생성이 망가짐(예전 14B의 medit 0점). 길수록(seq1024~2048) 긴 파일을 온전히 다룸 — 단 메모리↑. Linux 전환으로 seq256→1024로 8배 확장.
- **어댑터가 왜 이렇게 작나(263MB)?** 전체(14B=29GB)가 아니라 0.46%(68.8M)만 학습하니까. 베이스는 공유하고 어댑터만 갈아끼우는 게 LoRA의 이점.
